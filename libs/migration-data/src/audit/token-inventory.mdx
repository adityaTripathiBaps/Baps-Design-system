# Token Inventory & Reconciliation

Every semantic/component token in `libs/tokens/src/source/*.tokens.json` carries a `legacyMapping` field recording which events-ui CSS variable and/or spm-ui CSS variable it reconciles. This page explains the mechanism and gives a representative sample — the full machine-readable table is `libs/tokens/build/json/tokens.flat.json`, regenerated on every token build.

## How to read a reconciled token

```json
"text": {
  "muted": {
    "value": "{color.mybky.mono.500}",
    "legacyMapping": { "eventsUi": "--text-color-muted" }
  }
}
```

This means: the BAPS token `color.mybky.text.muted` replaces events-ui's `--text-color-muted`. Tokens with both `eventsUi` and `spmUi` keys are cases where a semantic *concept* exists in both products (e.g. "muted text color") even though the two brands' actual hex values differ — those are kept as separate `mybky.*` / `sampark.*` branches, not merged into one value, per the brand-scoping decision in `inconsistency-findings.mdx`.

## What's NOT yet reconciled

This inventory currently covers color primitives/semantics, typography, spacing, radius, shadow, motion, and component tokens for **Button, FormField, Badge, Avatar, ToggleSwitch** only — matching the Tier 1/2 priority components identified for both products. Still outstanding for Phase A: Checkbox/Radio, Select/Dropdown, Table/DataTable, Tabs, Tooltip, Overlay/Dialog z-index tiers (Sampark only, events-ui doesn't define an equivalent scale explicitly), and the full 900+ line events-ui `_light.scss` / 6800-line spm-ui SCSS set beyond what's captured here.
